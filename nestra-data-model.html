NESTRA Data Model

How NESTRA's data is organised: 8 modules, the three room states kept apart, an ERD for each module, and every 1:1, 1:N and M:N relationship. This is the design only. No SQL.

Draft for review.Based on the web and mobile Figma files and the decisions settled so far (commission and payouts #1, pinned 3D versions #7, platform billing). It hasn't been compared with the 69-table schema in NESTRA-GP/database, so some table names may differ.

Overview

Eight modules

Each module owns its own tables. Modules connect only through foreign keys. MySQL is the source of truth, MinIO holds the files, and Python services never write to the database directly.

Core rule

Three room states, never mixed

The real room, the proposed design and the furniture actually bought each live in their own tables. Data moves between them only through the explicit actions listed below.

AS-IS

The real room

What is physically there right now?room_revisions → walls, openings, room_objects
PLANNED

The proposal

What do we want the room to become?layouts → layout_versions → layout_items
PURCHASED

What was bought

What did the customer pay for, and at what price?orders → store_orders → order_items

The only bridges

  1. Design from reality. Every layout_version records the room_revision_id it was built on. A re-scan flags the layout as out of date.
  2. Buy from the design. cart_items and order_items keep the layout_item_id of the slot they fill. The layout item's status moves to ordered.
  3. Mark installed. Creates a new room_revision with a room_object that points to the order_item_id. The old revision is kept.
  4. Return. The layout item goes back to a generic placeholder in the same position. If it was installed, a new As-Is revision is created without it.

  A["AS-IS · room_revisions + room_objects"]
  P["PLANNED · layouts + layout_items"]
  B["PURCHASED · orders + order_items"]
  A -- "layout built on revision X" --> P
  P -- "layout_item → variant → cart → order" --> B

order_items copies the name, price and dimensions at purchase, so later catalogue changes don't touch past orders. Decision #1: NESTRA collects card and instalment payments and pays each store its share minus commission. For cash on delivery the store collects the money, and the commission is deducted from that store's next payout. The commission rate is copied onto each store order at checkout. The store's balance is always calculated from the ledger, never stored.

Design decisions

Why it's shaped this way

Revisions, not updates

Room revisions and layout versions are append-only. You can always see what a room or design looked like on any date.

Snapshots in orders

Order items copy name, price and dimensions. Store orders copy the commission rate. Past orders never change.

Stable object identity

object_key (e.g. LR-SOFA-01) follows one piece of furniture from placeholder to matched, ordered and installed.

Pinned 3D versions

A new model shows as "update available" and is used only when a new layout version is saved and validated again.

Decision #7 · Figma AS 05, EN 07

Ledgers, not balance columns

Store balances and AI credits are calculated from append-only ledgers with idempotency keys. No balance can drift.

Decision #1 · Figma SL 01, MK 10–11

JSON only where nobody searches

Dimensions, prices and statuses are real columns with indexes. JSON is used only for the address snapshot and raw scan output.
